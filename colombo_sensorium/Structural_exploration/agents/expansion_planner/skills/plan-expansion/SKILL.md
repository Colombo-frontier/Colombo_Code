# Plan a Setting Expansion Batch

1. Read `standards/expansion.md`, the frozen request, and `schema_read(expansion_plan)`. Distinguish source tasks from permitted target tasks. Identify fixed constraints, allowed changes, priority mode, maximum mutation steps, and all batch limits. Do not infer permission to add a task from a related seed.
2. Inspect the compact seed portfolio. Use `atlas_read` or `read_batch` for selected task, model, oracle, output, metric, and view fields. Inspect deeper material only when it changes a proposed transformation. A catalog's missing tag remains unknown; it does not prove that a property is absent.
3. Propose meaningful changes rather than keyword combinations. Consider native oracle substitution, statistical protocol, a model assumption on a specified object/block, a declared target or resource, a boundary, or an approved transfer to another task. Explain why this change exposes a useful distinction, information mechanism, application, or missing coverage.
4. Count primary conceptual transformations, not the number of fields requiring repair. A single approved layer transfer may require coordinated TASK/MODEL/ORACLE/OUTPUT/METRIC/RESOURCE definitions. List those dependencies explicitly, keep them within `allowed_axes`, and do not hide a second independent transformation in a dependency. Use a two-step proposal only when the request permits it and both steps have a clear purpose.
5. For one-level to bilevel transfer, identify the recipient level and objective/operator. Explain how the lower-level solution is selected and why the proposed outer target is defined. Distinguish primitive lower-level observations from access to an exact lower solution or reduced gradient. A transfer lead must include the missing cost or regularity argument.
6. Describe oracle/noise changes precisely enough to assess value: exact population values versus exact sample values, fresh versus reusable samples, conditional assumptions, and permitted query pairs. Do not assume that exact and noisy interfaces contain one another without a stated parameter or simulation model.
7. Flag directions likely to be an existing view, regime, or representation. Deterministic/randomized algorithms, confidence choices, and parameter endpoints should not be advertised as new top-level settings. Keep a useful direction if it may reveal an existing-profile update, but make its likely route clear; the matcher decides.
8. Rank with a brief reason. In `classical` mode emphasize foundational coverage and evidence routes; in `gaps` mode emphasize plausible unresolved comparisons with explicit uncertainty; in `balanced` mode combine coverage, conceptual value, and variety. Never label a setting open because its Atlas node or lower bound is missing. Avoid counting ten variants of the same mechanism as ten independent discoveries.
9. Save at most the requested opportunity limit. Record directions omitted for scope, dependence, low marginal value, or insufficient information. Do not expand an unreviewed proposed setting into another generation within this run. Hand off the plan references for controlled selection.
