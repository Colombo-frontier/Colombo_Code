# Setting Expander: Collaboration Protocol

Use the project protocol for immutable references, tools, recovery, and the small final handoff. Read `schema_read(candidate)` and `schema_read(expansion)` and `schema_read(expansion_origin)` first; they govern the concrete structures.

## Candidate provenance

The controller provides the frozen request/plan, selected opportunity, and authorized seed snapshots. Save a `candidate` with all eight axes, views, scoped `tag_facts`, and issues. Set `paper_refs=[]` when no actual triggering papers are supplied. Preserve authentic paper references only when their records exist and have the correct role.

Register `origin.kind=atlas_expansion`, the request and plan references, opportunity ID, and real seed references as required by the candidate schema. Pin the source setting versions through those snapshots. Newly chosen conditions are explicit definitions of the proposed contract. Do not attach a source citation claiming that a seed or paper proves a newly defined property. Empty evidence references for a definition are preferable to invented evidence.

## Main artifact

The main kind is `expansion`. Bind the exact `request_ref`, `plan_ref`, `opportunity_id`, and frozen `candidate_ref`. Record `changes` with axis, affected object, before/after statements, and reason. Explain nonemptiness, objective definition, oracle coherence, and nontriviality in `well_posedness`, including supporting checks and remaining unknowns. `selection_reason` explains the value of this exact candidate. Use scoped issues for genuine blockers; missing bounds alone do not make a complete contract invalid.

The expansion record is not a paper extraction bundle or an identity decision. It must not contain a declaration that the candidate is absent from all literature. Subsequent matcher/reviewer jobs make the Atlas identity judgment.

## Revision and handoff

Repair only the assigned opportunity. Preserve candidate ID and provenance, answer each feedback item, and distinguish corrected omissions from remaining scientific uncertainties. Changes to the contract create a new immutable candidate and require independent review. Do not silently change the target task or fixed constraints to eliminate a difficulty.

Return the frozen expansion reference in the shared handoff. `complete` means the assigned specification work is complete; the expansion review may still request revision or defer identity-critical questions.

## Parameter scope and later closure obligations

Preserve the full authorized parameter domain and explain joint variables, fixed structural parameters, uniform constants and any diagnostic slice in the existing candidate model/view fields. Do not replace the full request by a convenient accuracy-versus-dimension slice or hide a new oracle solve/cost. Endpoint or zero-query cases are guarded regimes, not new primary status codes. A designed complete contract can pass specification review with missing bounds; it is not an optimality or complete-literature certificate.

Later research must create joint-analysis v2, assess compatible/replacement/resource-projection routes, and publish proved closed regions natively or keep publication pending. Seed/neighbor labels and historical proofs grant no current approval. Use standards/joint_parameter_standard.md for a concrete scope question, without adding profile-only analysis fields to the candidate or doing the final profile review in this stage.
